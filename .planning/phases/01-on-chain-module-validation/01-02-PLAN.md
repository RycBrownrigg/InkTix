<objective>
Validate the three modules that `docs/v2_plan.md` and `CONCERNS.md` flag as the riskiest
on-chain ports, using targeted **runtime** edge cases rather than input-validation edge
cases (D-05; input sanitization is Phase 3 scope per D-06).

Each of these three is risky for a different reason, and each test is built to be
*discriminating* — to fail loudly if the specific risk is real:

- **pricing** — `time_multiplier` reads `ink::env::block_timestamp()`. Under `ink-node`'s
  manual-seal consensus blocks are authored per transaction rather than on a timer, and
  RESEARCH.md could not confirm what the timestamp inherent actually contains
  (assumption A1). The test reads the chain's own timestamp back out of storage and
  derives every event date from it, so the bucket assertions hold regardless of A1 —
  while a separate, explicitly-labelled assertion answers A1 itself.
- **loyalty / advanced_team_loyalty** — `Mapping<(Address, u32), TeamLoyaltyProfile>` is
  the single riskiest storage item in the contract. `stake_on_team` updates the profile
  inside an `if let Some(..) = storage.team_loyalty_profiles.get((user, team_id))`
  branch, so a composite key that fails to round-trip on a real chain does **not** error
  — it silently skips the update. Asserting the accumulated total after two stakes is
  therefore the only assertion that can detect the failure at all.
- **anti_scalping** — the `Vec<Address>` blacklist/whitelist round-trip under repeated
  mutation. There is no append message; `configure_anti_scalping` overwrites the whole
  config, so "append twice" means two full writes with a grown Vec.

Purpose: VALIDATE-01's success criterion explicitly names `stake_on_team()` composite-key
confirmation as required.
Output: `contracts/inktix/src/tests/e2e/risk_tier.rs` with three passing on-chain tests.
</objective>
